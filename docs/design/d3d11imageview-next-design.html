01 / SIMPLE DESIGNImageView → Impl → Engine + Layer로 시작한다

지금과 비슷한 구조로 충분히 만들 수 있다. 새 프로젝트에서도 ImageView가 공개 기능을 제공하고, Impl이 창·입력·렌더 흐름을 연결하며, Engine과 Layer가 실제로 그리게 한다.

앞선 제안은 기능별 책임을 분리하는 것을 구현 클래스의 분리로 너무 많이 옮겼다. 초기 범용 뷰어에 필요한 수준보다 관리 객체가 많았다. 이번 안은 사용자가 따라갈 호출 경로와 실제 소유 관계가 짧은 구조를 기준으로 다시 정리했다.

Impl은 연결한다

창·스레드·레이어 등록·입력 전달. 이미지 변환이나 도형 편집 알고리즘은 담당 레이어에 둔다.

Layer는 기능을 가진다

이미지는 ImageLayer, ROI는 ROILayer, UI는 UILayer. 관련 데이터와 동작을 가까이 둔다.

큰 기능만 보조 클래스로

타일 처리처럼 상태와 알고리즘이 충분히 큰 기능은 TileCache로 분리한다. 목록·큐마다 관리 클래스를 만들지 않는다.

바뀌지 않는 목표: 선택형 UI, 고해상도 타일, 외부 texture/shared pool, 사용자 레이어, 관성 팬, WPF 라벨링 확장. 기능은 그대로 목표로 두고 구현 구조를 단순하게 만든다.

현재도 C++20 설정이다. 새 코드에서는 RAII·표준 동기화·명확한 메모리 수명·공통 도형 함수를 적용한다. 클래스가 많아야 모던 C++인 것은 아니다.

코드 작성·학습 규칙 (2026-11-28 합의)

이 프로젝트의 실제 코드와 설명용 예제에서 표준 라이브러리 헤더를 include할 때에는 같은 줄에 // for 사용 이름을 적는다. 여러 이름을 사용하면 함께 나열한다.

#include <vector>   // for std::vector
#include <memory>   // for std::unique_ptr, std::make_unique
#include <utility>  // for std::move, std::exchange

설명 주석은 모든 줄의 동작을 반복하지 않는다. 헷갈리기 쉬운 동작, 설계 의도, 소유권·수명·동기화처럼 오해하면 문제가 되는 부분에 필요한 만큼 작성한다. 학습용 코드에도 해당 주석을 함께 제시하며, 사용자가 보고 타이핑할 주석을 선택한다.

확정된 구현 방침: ComPtr는 사용하지 않는다. COM 참조는 작은 자체 RAII 타입 ComRef<T>로 관리한다. 내부에는 raw pointer 하나를 보관하고 복사 시 AddRef, 소멸 시 Release한다. Attach는 기존 참조를 인수하고 CopyFrom은 참조를 추가한다. Engine과 Layer는 정리 순서를 책임지고, 반복적인 COM 참조 해제는 이 타입이 처리한다.

04 / OWNERSHIP한 객체를 두 곳에서 소유하지 않는다

layers가 모든 레이어의 유일한 소유자다. 특정 기능에 빠르게 접근하려고 보관하는 ImageLayer* imageLayer, ROILayer* roiLayer는 비소유 참조다. 레이어를 제거할 때 해당 참조도 비우며, 외부에서는 이 포인터를 보관하지 않는다.

FrameContext는 큰 관리 객체가 아니다. 이번 프레임의 Engine 참조, Camera 변환, 화면 크기, dt 등을 담는 작은 구조체다. 각 레이어가 필요한 것을 전역 변수나 Impl을 거쳐 찾아가지 않게 인수로 전달한다. 레이어는 context를 프레임 밖에 보관하지 않는다.

COM 포인터 관리: 복사 가능한 ComRef<T>

이름은 ComRef, 참조 인수는 Attach, 참조 추가는 CopyFrom으로 확정한다. COM 참조 하나를 관리하는 복사·이동 가능한 RAII 템플릿이다. 복사 시 AddRef, 소멸 시 Release한다. 별도 참조 카운트나 shared_ptr 관리 블록은 만들지 않고 COM 객체의 기존 카운트를 사용한다. 내부 공통 헤더에 두고 D3D11·DXGI·D2D·DirectWrite에 동일한 타입을 사용한다.

동작참조 수와 소유권 계약
기본 생성 / 소멸nullptr로 시작. 소멸 시 보유한 참조를 Release한다.
Attach(pointer)호출자가 가진 기존 소유 참조 하나를 인수. 새 포인터에 AddRef하지 않으며, 기존에 보관하던 참조는 Release한다. 호출자는 넘긴 참조를 더 이상 해제하지 않는다.
CopyFrom(pointer)빌린 포인터에 AddRef하여 자신의 참조 하나를 확보. 새 포인터를 먼저 AddRef하고 기존 참조를 Release하므로 같은 객체를 가리키는 경우에도 유효하다. nullptr이면 기존 참조만 정리한다.
복사 생성 / 복사 대입같은 COM 객체를 가리키고 AddRef한다. 복사 대입은 새 참조 확보 후 기존 참조를 Release한다. 자기 대입도 안전하게 처리한다.
이동 생성 / 이동 대입AddRef 없이 참조를 이전하고 원본을 nullptr로 만든다. 이동 대입은 목적지의 기존 참조를 Release한다. 자기 이동 대입은 참조를 잃지 않게 처리한다.
Get() / operator->잠깐 사용할 raw pointer 제공. 참조 수 변화 없음. 받은 쪽이 Release하지 않는다.
Put()빈 ComRef에만 COM 출력 인수 T** 제공. 보관 중인 포인터를 덮어쓰지 않는다. 생성·교체 시에는 빈 임시 ComRef를 사용한다.
Reset()보유 참조를 Release하고 nullptr로 만든다. 빈 상태에서도 안전하며 device lost·명시적 종료에 사용한다.
#include <utility>  // for std::move

ComRef<ID3D11Texture2D> displayTexture;

// 생성 실패 시 기존 표시 texture를 유지한다.
ComRef<ID3D11Texture2D> next;
HRESULT hr = device->CreateTexture2D(&desc, nullptr, next.Put());
if (FAILED(hr)) return hr;
displayTexture = std::move(next);

// 외부에서 빌린 texture를 비동기 처리까지 보관한다.
ComRef<ID3D11Texture2D> pendingTexture;
pendingTexture.CopyFrom(externalTexture); // AddRef

auto anotherRef = pendingTexture; // 복사 생성: AddRef
anotherRef = displayTexture;     // 복사 대입: 새 참조 확보 후 기존 참조 반환

// createdTexture는 생성 API가 성공 시 반환한 소유 참조다.
ComRef<ID3D11Texture2D> imported;
imported.Attach(createdTexture); // AddRef 없이 참조 인수
createdTexture = nullptr;        // 호출자에게 해제 책임이 남지 않음

Attach(ref.Get())처럼 빌린 포인터를 소유 참조인 것처럼 넘기지 않는다. Attach에는 실제로 이전할 참조 하나가 있어야 한다. 동일한 주소라도 별도로 확보한 소유 참조가 넘어올 수 있으므로, 포인터 주소만 같다고 무조건 건너뛰는 구현은 하지 않는다. 추가 참조가 필요한 경우에는 CopyFrom 또는 ComRef의 복사를 사용한다.

raw pointer를 받는 모호한 암시적 생성자·대입 연산자는 두지 않는다. raw pointer 경계에서는 Attach/CopyFrom으로 의도를 드러내고, ComRef 사이에서는 일반 복사·이동을 사용한다. 이 타입은 COM 객체 전체를 독점 소유하는 것이 아니라 자신이 가진 참조 한 개의 반환을 책임진다.

  • 정리 순서: Engine과 Layer의 ReleaseResources()에서는 필요한 순서로 Reset한다. 남은 참조는 멤버 소멸로 정리한다.
  • 스레드: ComRef의 복사 기능이 같은 포인터 변수에 대한 동시 접근이나 COM 인터페이스 사용을 자동으로 동기화하지 않는다. 렌더 스레드와 종료 경계를 유지한다.
  • GPU 동기화: AddRef는 객체 수명만 유지한다. 생산자의 동시 쓰기, GPU 읽기 완료, frame lease 반환은 별도 동기화가 필요하다.
  • 검증: 가짜 COM 객체로 복사 생성·대입·자기 대입·이동·자기 이동·Attach·CopyFrom·Reset·소멸의 참조 수를 확인한다. 같은 객체에 대한 CopyFrom과 별도 참조를 인수하는 Attach도 포함한다.

기본은 뷰마다 Engine 하나

시작부터 여러 창이 device를 공유하는 복잡한 관리 구조를 만들지 않는다. 기본은 뷰어 한 개가 Engine 한 개를 소유하고 하나의 렌더 스레드가 사용한다. 여러 창을 실제로 연결해 메모리·지연 문제가 확인되면, 그때 Engine 공유 방식을 별도 설계한다.

공유가 필요한 시점에는 Engine을 shared_ptr로 바꾸는 것만으로 끝나지 않는다. 같은 immediate context의 직렬 실행, 화면별 출력, 모든 창의 device lost 복구를 함께 조율해야 한다. 이 제약은 후속 작업으로 명확히 남긴다. 다른 device에서 생산한 shared texture 입력은 기본 구조에서도 지원한다.

05 / CALL FLOW호출 흐름도 몇 단계면 충분하다

이미지 표시

앱: view.SetImage(image)
  → Impl: 이미지 교체 예약 + 렌더 깨우기
  → ImageLayer: 원본 수명 확보 / texture 또는 TileCache 준비
  → ImageLayer::Render(): 그림
  → Engine::EndFrame(): 화면 출력

마우스 입력

창 메시지 → Impl::HandleInput()
  → capture 중인 대상이 있으면 그 대상에 전달
  → popup / 위쪽 UI·사용자 레이어부터 처리 기회
  → ROILayer: 선택·편집
  → 처리되지 않은 navigation 입력은 Camera: 줌·팬

입력 순서는 그리기 순서의 역순을 기본으로 하되, drag capture가 우선한다. capture는 작은 target ID로 기록하면 된다. 마우스를 누른 대상과 뗄 때 받는 대상이 달라지지 않게 하고, 창 비활성·capture loss 때 Cancel을 보낸다.

  3. layers의 Prepare(context) 호출
  4. Engine.BeginFrame()
  5. layers를 순서대로 Render(context)
  6. Engine.EndFrame()
  7. 애니메이션·타일·새 frame이 남으면 예약, 없으면 대기

레이어 항목에 stage + order 값만 둔다. 이미지의 D3D 단계와 overlay/UI의 D2D 단계를 구분하고, Impl이 단계 경계에서 Engine의 begin/end 함수를 호출한다. 사용자 레이어가 BeginDraw/EndDraw/Present를 직접 호출하지 않게 한다. 순서 정렬과 실행은 짧은 함수로 충분하다.

단순하게 유지해도 지켜야 할 수명 규칙

  • GPU context는 렌더 스레드에서 사용. UI는 예약 상태나 유한 queue를 통해 요청한다.
  • CPU 입력은 동기 복사 또는 owner/lease를 함께 넘김. span이나 raw pointer만 비동기 queue에 남기지 않는다.
  • release·편집 완료 같은 사용자 콜백은 내부 lock 밖에서 호출한다. 콜백에서 Close를 요청할 수 있지만 자신의 종료를 동기 대기하지 않는다.
  • Close는 새 입력 차단 → 타일 작업 취소 → pending 반환 → GPU 사용 정리 → 레이어 → Engine 순서다. HWND는 UI 스레드에서 정리하고, 종료 완료 뒤에는 callback이 남지 않는다.
  • 입력 좌표는 실제 표시된 camera 변환을 기준으로 계산한다. 확대 중인 목표 배율과 화면에 표시된 배율을 혼용하지 않는다.

D3D11의 device와 immediate context는 스레드 규칙이 다르다. Microsoft: D3D11 멀티스레딩

06 / LAYERS커스텀 기능도 기존처럼 Layer로 확장한다

그래프·차트·특수 표시를 추가하려면 사용자 Layer를 등록하면 된다. 새로운 Component·Pass·Canvas 계층을 모두 도입하지 않는다. 한 번 그리는 기능에는 callback을 감싼 작은 Layer도 제공할 수 있다.

// 개념 예시. C++ 앱은 같은 SDK / 툴체인 조건에서 사용한다.
class Layer {
public:
    virtual ~Layer() = default;
    virtual void Prepare(FrameContext&) {} // upload·자원 준비
    virtual void Render(FrameContext&) = 0;
    virtual bool OnInput(const InputEvent&) { return false; }
    virtual void OnDeviceLost() {}          // GPU 자원만 비움
};

class GraphLayer final : public Layer {
public:
    void Render(FrameContext& frame) override;
};

auto graphId = view.AddLayer(
    std::make_unique<GraphLayer>(), LayerPosition::AboveROI);
view.RemoveLayer(graphId);

레이어 등록 시 소유권은 뷰어로 이전한다. 그리는 중에 RemoveLayer가 들어오면 다음 안전한 경계에서 제거하고 완료를 알린다. callback이 참조하는 데이터와 외부 DLL은 제거 완료까지 살아 있어야 한다. 이것은 별도 Registration 서비스 없이 ID와 완료 통지로도 구현할 수 있다.

도형의 공통 표현은 Shape = variant<Rect, Ellipse, Polyline, Polygon, ...> 같은 값 데이터로 두고, OverlayLayer와 ROILayer가 같은 DrawShape()를 사용한다. 도형마다 OverlayRenderer와 ROIRenderer를 각각 만들 필요가 없다. 선택 핸들·편집 계산은 ROILayer에 추가한다.

일반 확장은 공통 도형/텍스트 함수를 사용하고, 특별한 shader가 필요한 Layer만 렌더 스레드의 D3D context를 제한적으로 사용한다. Engine은 다음 layer에 필요한 pipeline 상태를 다시 설정한다. D2D state block만으로 clip stack이나 D3D 상태 전부가 복구된다고 약속하지 않는다. D2D drawing state 구성

Layer 단위는 사용자에게 보이는 기능 묶음이다. 픽셀 격자는 ImageLayer의 표시 옵션, 선택 핸들은 ROILayer의 기능으로 시작해도 된다. 독립적인 순서·교체가 필요해질 때에만 별도 layer로 뺀다.

07 / LARGE IMAGE타일은 TileCache 하나로 묶고 내부부터 제대로 만든다

ImageLayer가 작은 이미지를 texture 하나로 처리하고, 큰 이미지일 때 TileCache를 생성한다. TileCache 내부에 cache·작업 queue·worker·예산·우선순위를 멤버로 둔다. 각각을 Scheduler, Pipeline, Service로 이름 붙여 독립 객체로 만들 필요는 없다.

ImageLayer
  ├─ 일반 이미지 → texture 하나
  └─ 큰 이미지   → TileCache
                    ├─ 원본 ImageSource 참조
                    ├─ 필요한 타일 계산 / LOD 선택

                    ├─ 준비된 CPU 타일 / GPU 타일
                    └─ 메모리·업로드 예산

RAM 버퍼와 거대 이미지 파일은 읽는 방법이 다르다. ReadRegion(level, rect)처럼 필요한 부분을 읽는 작은 계약을 두면 TileCache는 파일 형식을 몰라도 된다. 처음에는 MemoryImageSource만 구현하고, 실제로 큰 파일을 지원할 때 파일 어댑터를 추가한다. 모든 소스에 interface 계층을 여러 단계 만들지는 않는다.

08 / TEXTURE INPUT공유 텍스처도 ImageLayer의 기능으로 둔다

풀 등록은 ImageLayer::RegisterTexturePool(), frame 접수는 SubmitFrame(), 실제 소비는 Prepare()로 충분하다. SharedSlot과 PendingFrame은 작은 데이터 구조체이며 서비스 계층이 아니다.

PendingFrame에 포함할 값

  • NT handle과 legacy handle은 명시적으로 구분하고 등록 때 한 번 열어 둔다. NT의 소유/복제/Close 규칙과 legacy 수명을 섞지 않는다.

  • frame 접수 성공, source를 다시 써도 되는 시점, 실제 화면 표시 시점을 구분한다. GPU 읽기와 다음 쓰기의 순서는 keyed mutex/fence 등 합의된 방식으로 보장한다.

10 / UI & WPF내장 UI를 선택하고 WPF를 얇게 연결한다

UILayer는 없을 수도 있다

UI를 쓰지 않는 구성에서는 UILayer를 만들지 않는다. 일부만 숨길 때에는 toolbar/statusbar/menu 표시 옵션을 사용한다. 숨긴 메뉴가 capture나 입력을 유지하지 않도록 처리한다. SetZoom(), SetLut() 같은 기능은 UI 존재와 관계없이 호출할 수 있다.

D3D11UIFramework의 버튼·패널·아이콘은 필요한 부분을 활용해도 된다. 먼저 빼야 할 결합은 Button 내부의 Zoom/LUT/SaveImage 전용 명령이다. 버튼은 command ID나 callback만 갖고, UILayer가 뷰어의 공통 API에 연결한다. toolbar와 menu는 같은 명령 설명 데이터를 재사용한다.

WPF 앱의 첫 구성

WPF 창
  ├─ 프로젝트·라벨 목록·속성·툴바: WPF
  └─ HwndHost
       └─ ImageView (UILayer 없음)
            ├─ ImageLayer

HwndHost는 간단한 시작점이다. 이미지 내부 ROI와 편집 핸들은 native layer에서 그리고, 주변 업무 UI는 WPF로 만든다. 같은 영역 위에 WPF 요소를 자유롭게 겹쳐야 하는 요구가 생기면 별도 합성 경로를 검토한다. HWND airspace 제약은 그대로 존재한다. WPF/Win32 interop

D3DImage는 Direct3D9 surface를 받으므로 D3D11 texture를 직접 전달할 수 없다. 필요하면 Engine의 offscreen 출력과 D3D9Ex bridge를 추가하되, 처음부터 Presenter 계층 전체를 만들지는 않는다. adapter·format·동기화·front buffer 복구를 작은 sample로 먼저 검증한다. D3DImage 호스팅

C++는 PImpl API로 시작하고, WPF에는 얇은 C ABI와 SafeHandle 래퍼를 붙인다. callback은 Dispatcher로 전달하고 종료 완료 후 delegate를 해제한다. ABI 안정성이 필요한 경계에서 STL·예외를 직접 넘기지 않는다. 프로젝트 전체를 API framework로 만드는 것은 목표가 아니다.

12 / GUIDED DEVELOPMENT직접 타이핑하는 개발 커리큘럼과 예상 시간

설명을 듣고 직접 타이핑하며, 매 단계의 실행 결과를 확인하는 과정으로 진행한다. 처음에는 창과 Engine만 만들고, 이미지 → Camera → Layer 순서로 필요한 구조를 늘린다.

최종 설계도는 도착점이다. 0단계부터 Impl·레이어·작업 스레드·공유 풀을 모두 만들지 않는다. 단일 스레드의 작은 프로그램을 먼저 완성하고, 기능이 늘어나는 시점에 직접 구조를 옮겨 본다.

시간 추정의 기준

  • C++ 클래스·포인터·기본 STL과 Win32 메시지 처리 경험이 있고, Direct3D 세부 원리는 설명을 들으며 복습한다고 가정한다. 기존 구현 경험을 반영한 개인 학습용 추정이다.
  • 아래 시간에는 개념 설명, 직접 타이핑, 컴파일 오류 수정, 실행 확인, 짧은 복습이 포함된다. 코딩만 자동으로 생성하는 시간과 다르다.
  • 프로젝트는 신규 C++20/x64, GPU는 우선 한 종류, 기본은 뷰마다 Engine 하나다. ComPtr 대신 자체 RAII ComRef<T>를 사용한다.
  • 예측하기 어려운 드라이버·환경 문제, 장기 중단 후 재학습, 큰 요구 변경은 단계별 범위에 충분히 담기 어렵다. 전체 일정에는 별도 여유를 둔다.
  • 기존 UIFramework의 사용 가능한 버튼·패널·아이콘을 활용하는 기준이다. UI toolkit 전체를 새로 만드는 시간, 완성된 CVAT 수준의 업무 앱, D3DImage 합성 bridge는 별도다.

위 순서는 스트리밍 기능을 먼저 확인하는 권장 순서다. 기본 과정 뒤에는 11 → 14~16으로 타일을 먼저 진행하거나, 11 → 17~20으로 라벨링을 먼저 진행할 수 있다. 기능 의존성이 없는 블록의 순서를 조정할 뿐, 생략한 블록의 시간까지 완료한 것으로 계산하지 않는다.

한 번의 수업은 60~90분 정도로 나눈다

  1. 5분: 이전 코드의 호출 흐름과 오늘 화면에서 확인할 결과를 짚는다.
  2. 10~15분: 이번에 필요한 개념과 변수의 소유자를 설명한다.
  3. 25~35분: 함수 1~2개 또는 약 30~80줄 단위로 설명을 듣고 직접 타이핑한다. 분량은 개념의 난도에 맞춘다.
  4. 15~25분: 빌드·실행하고 예상 결과와 비교한다. 오류가 있으면 원인을 이해한 뒤 고친다.
  5. 5분: 핵심 흐름을 직접 설명하고 다음 세션의 시작 지점을 남긴다.

새 파일을 만들 때에는 “왜 지금 필요한가 → 누가 소유하는가 → 누가 호출하는가 → 이번 단계에서 어디까지 구현하는가” 순으로 설명한다. 앞으로 구현할 기능 때문에 빈 클래스를 미리 늘리지 않는다. 엔진 생성과 이미지 출력도 한 번에 완성 코드를 옮기지 않고, 실행되는 작은 상태를 차례로 만든다.

당장 구현하지 않은 항목은 단계 번호로 적어 둔다. 예를 들어 8단계의 레이어 제거는 단일 스레드 기준이고 11단계에서 비동기 제거를 보강한다. 14~15단계의 동기 타일 생산은 학습용 중간 상태이며 16단계에서 worker로 옮긴다. 2단계의 resize·정상 해제는 바로 구현하고, 전체 device 복구는 23단계에서 완성한다.

진행 기록과 시간 보정

각 단계가 끝나면 실제 시간, 완료한 실행 결과, 남은 의문, 다음 시작 함수만 짧게 기록한다. 0~3단계 후 첫 재산정, 10단계 기본 DLL 후 두 번째 재산정, 13·16단계의 GPU 동기화와 타일 검증 후 마지막 확장 범위를 조정한다. 이해가 어려운 부분은 설명과 실험 시간을 늘리고, 이미 익숙한 부분은 빠르게 통과한다.

첫 수업 목표: 신규 테스트 창을 만들고 생성·메시지·종료 흐름을 확인한다. 다음에 ComRef를 만든 뒤 D3D11 device와 swapchain을 생성한다. Layer 개념은 이미지와 Camera가 작동한 후 8단계에서 도입한다.

14 / SOURCES분석 범위와 참고 자료

이 문서는 신규 프로젝트의 설계 제안이다. 기존 코드에 대한 정적 분석을 바탕으로 작성했으며 GPU 실행·성능을 새로 검증한 결과는 아니다. 잠재 경합은 재현된 버그와 구분했다. 이 수정에서는 기존 C++ 소스를 변경하지 않았다.

기존 구조는 참고하되 새 프로젝트에서 시작한다는 목표를 유지한다. 제안 클래스명은 가칭이고 현재의 D3D11ImageView, ImageRenderLayer, ROIRenderLayer 이름을 그대로 사용해도 된다.

  • NT / legacy 공유 핸들

  • Flush의 비동기 동작
  • D3D11.2 tiled resources
  • D2D drawing state
  • WPF airspace
  • D3DImage 호스팅
