이 모듈은 검사·계측용 이미지 뷰어다. 산업용 카메라가 만드는 수억 픽셀 이미지를 지연 없이 보고, 그 위에 측정 도형(ROI)을 얹고, 픽셀 값을 직접 읽는 것이 요구사항이다.

설계의 중심에는 하나의 긴장이 있다. 큰 이미지는 전부 GPU 에 올릴 수 없고, 작은 이미지에 타일링을 걸면 순전히 낭비다. 두 경로를 다 만들고, 그 사이를 자동으로 가르는 판정을 두는 것이 이 모듈의 뼈대다.

임베딩 컴포넌트로 만든 이유

Initialize(HWND parent, RECT, style, engine) 하나로 자식 창이 생긴다. 호스트는 MFC 다이얼로그일 수도, WPF 창일 수도, 다른 Win32 앱일 수도 있다.

D3D11 렌더 엔진은 외부에서 주입받거나 직접 만든다. 주입받는 경우는 호스트가 이미 D3D11 을 쓰고 있어 디바이스를 공유해야 할 때다 — 그때는 immediate context 게이트도 같이 받아 직렬화한다.

코드 구조

공개 표면 한 겹, 구현은 관심사별 6개 파일, 그 아래 레이어 7개.

레이어 순서가 곧 정책이다

픽셀 격자가 ROI·오버레이 위에 있다. 격자는 이미지를 읽기 위한 보조선이라 ROI 에 가려지면 쓸모가 없기 때문이다. UI 는 언제나 맨 위다.

순서를 배열 하나(m_layers)로 표현하고 Initialize 에서 한 번 정한다. 레이어를 추가할 때 어디에 끼울지 정하는 것 말고는 할 일이 없다.

렌더 파이프라인

프레임 한 장. 그리지 않는 경로가 그리는 경로만큼 중요하다.

왜 유휴 직후 프레임의 dt 를 0 으로 두는가

렌더 스레드는 할 일이 없으면 잠든다. 그래서 유휴 후 첫 프레임의 dt 에는 유휴 시간이 통째로 들어있다(타이머가 0.1초로 클램프).

그대로 보간에 넣으면 Camera2D 의 보간 속도 14 기준 k = 1 − exp(−14 × 0.1) = 0.75 — 첫 프레임에 목표까지 거리의 75%를 소비한다. 휠을 한 칸 돌렸을 때 애니메이션 없이 곧바로 목표 배율로 튄다. (휠을 연타하면 스레드가 잠들지 않아 dt 가 정상이고 부드럽게 보인다 — 증상이 조작 속도에 따라 달라져서 원인을 찾기 어려웠던 부류다.)

D2D 순서 보장이 없는 자리

픽셀 격자는 이번 프레임에 보이는 값들의 비트맵을 Prepare() 에서 만든다. 프레임의 BeginDraw 안에서 오프스크린 타깃에 그리면 D2D 가 순서를 보장하지 않아 비트맵이 비어 버린다.

같은 이유로 이미지 알파를 셰이더에서 1.0 으로 고정한다. D2D 타깃이 PREMULTIPLIED 라 4채널 소스의 알파가 그대로 백버퍼로 새면 그 위 오버레이 블렌딩이 틀어진다.

동시성 모델

스레드 둘. 그 사이를 락 하나와 원자 플래그 하나로 잇는다.

스레드하는 일동기화
UI 스레드 (호스트) 창 메시지 · 입력 · UpdateImage · 오버레이/ROI 조작 대기 슬롯에 적재 후 InvalidateFrame()
렌더 스레드 프레임 구성 · 타일 생산 · D3D/D2D 드로우 m_renderLock 을 쥐고 Render() 전체를 수행

온디맨드 렌더 — 움직이지 않으면 그리지 않는다

RenderThread 는 애니메이션이 없고 요청도 없으면 조건변수에서 잠든다. 입력이 들어오면 RequestFrame() 이 깨운다. 검사 장비의 뷰어는 대부분의 시간 정지 화면을 보여주므로, 60fps 로 계속 도는 것은 순전히 전력과 GPU 시간의 낭비다.

페이싱은 고해상도 waitable timer 가 담당한다. 프레임 간격은 volatile LONG64 에 100ns 단위 정수로 들고 있다 — Interlocked 계열에 double 오버로드가 없고, 어차피 SetWaitableTimer 가 원하는 단위가 100ns 라 나눗셈도 설정 시점 한 번으로 옮겨간다.

고해상도 타이머를 얻지 못한 환경에서만 timeBeginPeriod(1) 로 내려간다. 정상 경로에서 거는 것은 전력만 더 쓰는 일이라 조건을 달았고, 참조 카운트 방식이라 건 만큼만 푼다.

종료에서 놓치기 쉬운 창 하나

RequestStop();

// 정지 플래그를 세운 직후 바로 깨우면 놓칠 수 있다.
// 렌더 스레드는 락을 쥔 채 술어를 평가한 뒤 SleepConditionVariableSRW 로
// 진입하는데, 그 사이에 WakeConditionVariable 이 끼면 대기자가 아직 없어
// 무효화되고 스레드는 INFINITE 로 잠들어 Join 이 영구 대기한다.

AcquireSRWLockExclusive(&m_renderLock);    ← 락을 한 번 통과시킨다
ReleaseSRWLockExclusive(&m_renderLock);
WakeConditionVariable(&m_cv);

락을 통과시키면 두 경우 중 하나가 보장된다 — 렌더 스레드보다 먼저 잡으면 그쪽이 정지 플래그를 보고 잠들지 않고, 나중에 잡으면 이미 대기자로 등록돼 있어 깨움이 유효하다. 세 줄로 해결되지만 없으면 종료가 영구 대기한다.

이미지 버퍼의 수명 — DetachImage()

UpdateImage 는 버퍼를 복사하지 않고 포인터를 빌려간다. 렌더 스레드가 프레임 중에 그 메모리를 읽으므로, 호스트는 "언제까지 살려둬야 하는지 알 방법이 없었다." 

viewer->DetachImage();     1. m_renderLock 획득 — 렌더 스레드가 Render() 밖임을 보장
                            2. 대기 중인 이미지 업데이트 폐기 (그 안의 rawData 도 호출자 버퍼)
                            3. 풀 해제 + ImageBase::ReleaseBuffer()
buffer.Release();           ← 이제 안전
buffer.Build(...);
viewer->UpdateImage(buffer.Data(), ...);

TestHost 가 원래 Release() 를 먼저 불러 0xC0000005 로 죽었다 — 이 API 는 그 수정이다

Single / Tiled 판정

두 경로를 다 만들고, 어느 쪽으로 갈지는 이미지가 정한다.

왜 면적이 아니라 변 단위인가

Feature Level 11 의 Texture2D 한 변 최대가 16,384 다. 30,000 × 2,000 은 면적으로는 작지만 변 하나가 한계를 넘어 단일 텍스처로 만들 수 없다. 면적만 보면 이 입력에서 조용히 실패한다.

Gray 를 R8 로 두는 것이 판정을 바꿨다

백버퍼는 D2D interop 요구 때문에 B8G8R8A8 이지만, SRV 로 바인딩하는 소스 텍스처는 그 제약을 받지 않는다. Gray 를 R8 로 두면 VRAM 과 업로드 대역폭이 1/4 이 되고 변환 자체가 없어진다.

효과가 판정까지 바꿨다 — 8192² Gray 가 BGRA 기준 358 MB 라 Tiled 였는데, R8 로 85 MB 가 되면서 예산(128 MB) 안에 들어와 Single 로 승격됐다. 타일링 경로를 아예 타지 않으므로 이득이 크다.

타일링과 LOD

이 모듈에서 가장 어려웠고, 가장 큰 개선이 나온 자리.

원인은 상수 하나였다

타일 시스템은 이미 있었는데 큰 이미지에서 영구 스래싱이 났다. 원인을 찾아보니 maxLOD = 4 하드코딩이었다. 

// LOD4 타일이 덮는 원본 범위
512 × 2⁴ = 8,192 px

// 30만px 이미지를 fit 줌으로 보면
300,000 / 8,192 = 36.6  →  37 × 37 = 1,369 장

// 그런데 풀 용량은
lods = {512,200},{512,100},{512,50},{512,30},{512,20}   ← LOD4 는 20칸

1,369 장이 필요한데 20 칸이다. 매 프레임 전부 축출되고 전부 다시 만들어진다. 수렴할 수 없는 구조였다.

공식으로 바꿨다

maxLOD   = ceil(log2(imageMax / viewMin))
gridW    = ceil(viewW / 512) + 1
gridH    = ceil(viewH / 512) + 1
작업세트  = gridW × gridH
용량[L]  = min(전체타일수[L], 작업세트 × 2)

min(전체타일수, …) 이 maxLOD 를 자동으로 전량 상주시킨다. maxLOD 의 정의상 그 레벨의 전체 타일 수가 작업세트 이하로 보장되기 때문이다 — 그래서 부모 fallback 이 항상 성공한다. 구멍이 원리적으로 사라진다.

같은 30만px fit 줌에서 필요한 타일이 9~25 장이 된다. 이미지마다 Configure() 로 풀을 재구성하고, 뷰포트가 작업세트나 maxLOD 를 바꿀 때만 재구성한다 — 창을 몇 픽셀 끄는 것으로는 재생성하지 않는다.

프라이밍 — 채워지는 과정을 보여주지 않는다

PrimeCoarsestLevel() 이 maxLOD 레벨 전체를 예산 무시하고 한 번에 채운다. 그 전에는 RenderTiled() 가 이미지를 그리지 않는다.

결과적으로 타일이 하나씩 채워지는 과정이 노출되지 않고 준비되면 한 번에 나타난다. 참고한 기존 뷰어는 캐시가 준비되기 전 SwapBuffers 를 생략하는 방식이었는데, 그쪽은 카메라 행렬을 낡은 것으로 되돌려 위치가 밀리는 부작용이 있었다. 레이어 단위로 막으면 그 문제가 없다.

업로드 예산을 장수에서 시간으로

원래 MAX_UPLOAD_PER_FRAME = 4 였다. 그런데 LOD0 의 memcpy 와 고LOD 의 스트라이드 샘플링은 비용이 수십 배 차이난다 — 장수로는 프레임 시간을 예측할 수 없다. 2 ms 시간 예산으로 바꿨다.

모션 게이팅

Camera2D::IsSettled() 가 false 면 신규 타일 생성을 보류하고 상주분으로만 그린다. 드래그 중 스치는 타일은 업로드가 끝나기 전에 화면을 벗어나므로 그 비용이 순수 낭비다.

현재 프레임 타일이 축출되던 버그

EvictLRU 가 usedList.back() 을 무조건 가져갔다. 그런데 TileManager 가 이전 프레임 타일들의 lastFrameUsed 를 갱신하면서 usedList 순서와 어긋났고, 그래서 지금 화면에 보이는 타일이 축출될 수 있었다.

lastFrameUsed == frameID 인 타일을 스킵하도록 고치고, m_previousVisibleTiles 갱신도 frameID − 1 로 옮겨 현재 프레임 보호와 충돌하지 않게 했다.

구현하고 되돌린 것

타일 워커 스레드 풀 — 동작까지 확인하고 롤백했다.

타일 생산을 워커 스레드로 옮기면 렌더 스레드가 memcpy 에 묶이지 않는다. 구현해서 동작까지 확인했고, 프라이밍 1회가 약 10 ms → 4 ms 로 줄었다. 그리고 되돌렸다.

되돌린 이유

  • 이득이 얇다. 현재 목표(16300²급 정지 영상)에서 프라이밍 1회 6 ms 다. 값어치는 라이브 뷰나 30,000px 이상에서 나오는데 그 요구가 아직 없다.
  • 리스크가 최고 구간이다. 축출 보호 · 취소 · 수명 세 축이 모두 정확해야 동작한다. 하나만 어긋나도 증상이 "가끔 타일이 깨진다" 로 나타난다.
  • 미검증 코드 위에 쌓는 형국이었다. 앞선 단계들이 아직 육안 검증 전이었다. 문제가 생기면 워커 탓인지 앞 단계 탓인지 가를 수 없다.

보류 — 요구가 생기면 재적용
되돌린 것을 기록으로 남기는 이유

구현해 놓고 지우면 같은 아이디어가 6개월 뒤에 다시 올라온다. 그때 "해봤는데 이득이 6 ms 였고 리스크는 이러이러했다" 를 답할 수 있어야 같은 작업을 두 번 하지 않는다.

그리고 이 롤백이 버그 하나를 건졌다 — DetachImage 가 고친 수명 위반은 워커와 무관하게 존재했고, 워커를 붙이는 과정이 없었으면 발견이 늦었을 것이다.

인코딩 예외를 문서에 남겼다

프로젝트 규칙은 "모든 파일 UTF-8 with BOM" 인데 .hlsl 은 BOM 을 넣으면 FXC 가 거부한다 (error X3000: Illegal character in shader file). 그래서 셰이더만 BOM 없는 UTF-8 로 저장했고, 규칙의 예외라는 사실을 문서에 적었다. 적지 않으면 다음 사람이 "규칙 위반" 으로 보고 되돌린다.

검증

전용 호스트를 먼저 만들었다. 합성 이미지가 결함을 드러내도록 설계했다.

TestHost 는 뷰어를 구동하는 Win32 앱이다. 실제 이미지 파일이 아니라 결함을 드러내도록 설계한 합성 이미지를 쓴다.

합성 요소무엇을 드러내는가
체커보드축소 시 에일리어싱 — 밉맵이 동작하는지
그라디언트채널 순서 — R8 스위즐, BGR 확장, BGRA 알파
512px 격자선타일 경계 이음새와 좌표 정렬 (타일 크기와 같은 주기)
1024px 간격 1픽셀 점밉 필터가 미세 결함을 씻어버리는지 — 검사 용도에서 중요

크기 프리셋 6종 × 채널 3종(Gray / BGR / BGRA)을 전환하며 돌린다. 전환 자체가 테스트다 — 모드가 바뀌면서 리소스를 제대로 해제하는지, DetachImage 패턴이 지켜지는지가 그때 드러난다.

마지막 1픽셀 점이 도메인 질문을 남겼다

밉 필터가 1픽셀 결함을 씻어버린다. 일반 뷰어라면 개선이지만 검사 장비라면 그 1픽셀이 찾으려던 것일 수 있다.

기술적 정답이 없는 자리라 "max 필터 밉 체인이 필요할 수 있다(도메인 판단)" 로 남겨 뒀다. 결정할 수 없는 것을 결정한 척하지 않는 것도 문서의 일이다.

C# 바인딩과 WPF 예제

D3D11ImageViewC 가 C++ 클래스를 C API 로 평탄화하고, 그 위에 P/Invoke 바인딩과 WPF 예제가 있다. 예제는 문서이자 API 가 실제로 쓸 만한지 보는 검증이다 — 자기 코드로만 부르면 불편한 API 를 불편한 줄 모른다.

트레이드오프와 한계

고르지 않은 것들, 그리고 남은 것.

의도적으로 포기한 것

  • 타일 워커 스레드 풀 — 구현하고 되돌렸다. 설계는 문서에 남겼다.
  • RAM 피라미드 — 최대 변 20,480px 초과부터 의미가 생긴다(stride ≥ 8). 참고한 뷰어가 피라미드 없이 실전 사용 중이라, 앞 단계 효과를 실측한 뒤 재평가하기로 했다.
  • 타일 컴퓨트 셰이더 경로 — 삭제했다. GPU 는 이미 GPU 에 있는 데이터만 샘플링할 수 있는데, 고LOD 타일의 소스 범위는 어떤 스테이징 윈도우로도 담을 수 없다. 실제로 lod ≤ 3 게이트가 걸려 있어 정작 도움이 필요한 LOD4 이상에서는 비활성이었다.

남아 있는 것

  • ImageSpace 반픽셀 오프셋 — 오버레이·ROI 렌더러 7개 파일이 이미지 좌표에 +0.5f 를 더한다. strokeWidth 는 /scale 로 보정하는데 좌표는 안 한다. zoom 8 에서 ROI 경계를 보면 즉시 판별된다. 육안 확인 대기 중이다.
  • 오버레이 ID2D1PathGeometry 를 프레임마다 재생성한다. 렌더러에 캐시하면 되지만 아직 병목으로 드러나지 않았다.
  • syncInterval = 0 고정 — 티어링이 보인다. 정지 영상 뷰어라 문제되지 않지만 동영상 용도면 모드 분기가 필요하다.
  • 30만px 실측 미완 — 90 GB RAM 이 필요하다. 공식은 맞지만 그 규모에서 실제로 도는지는 확인하지 못했다.

이 모듈에서 얻은 것

가장 크게 배운 것은 성능 문제의 원인이 대개 알고리즘이 아니라 상수라는 점이다. 타일 스래싱의 원인은 정교한 캐시 정책이 아니라 maxLOD = 4 한 줄이었다. 비교 대상이던 다른 뷰어와 샘플링 방식은 동일했고 읽는 양이 38배 달랐다. 구조를 바꾸기 전에 숫자가 어디서 나왔는지부터 따라가는 것이 빨랐다.

두 번째는 되돌릴 수 있게 작업하는 것이다. 워커 풀은 구현·검증·롤백까지 하루 안에 끝났는데, 그게 가능했던 이유는 동기 경로를 폴백으로 상시 유지했기 때문이다. "되돌릴 수 있다" 는 전제가 있으면 고위험 변경을 훨씬 과감하게 시도할 수 있다.
