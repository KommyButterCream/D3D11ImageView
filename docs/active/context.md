# 맥락 노트 — 타일링/LOD 리팩터링

최종 갱신: 2026-08-23

---

## 1. 이 작업의 출발점

GLViewer_2DEngine(OpenGL)이 30만px 이미지를 부드럽게 렌더링하는 반면
D3D11ImageView는 큰 이미지에서 무너졌다. 두 프로젝트를 비교 분석한 결과
**샘플링 방식은 동일**했고(둘 다 stride 점 샘플링), 차이는 **읽는 양**이었다.

```
D3D11ImageView (이전)   maxLOD 4 고정 → fit 줌에서 1,369 타일 필요 / 풀 20칸 → 영구 스래싱
GLViewer                maxLOD 동적   → 9 블록
```

원인은 알고리즘이 아니라 **`maxLOD` 하드코딩** 하나였다.

---

## 2. 오늘 확정한 설계 결정

### maxLOD 정의 — GLViewer 의 `CalcMaxLODLevel` 과 동일하게

```
maxLOD = ceil(log2(imageMax / viewMin))
```

grid span 기반으로 잡으면 fit 줌에서 `SelectLOD` 가 clamp 되어 축소 에일리어싱이
생긴다. 타일 텍스처는 `MipLevels = 1` 이라 밉으로 완화되지 않는다.

### 용량 공식

```
작업세트 = (⌈viewW/512⌉+1) × (⌈viewH/512⌉+1)
capacity[L] = min(전체 타일 수[L], 작업세트 × 2)
```

`min(whole, ...)` 이 **maxLOD 를 자동으로 전량 상주**시킨다.
maxLOD 정의상 그 레벨의 전체 타일 수가 작업세트 이하이기 때문이고,
그 덕에 **부모 fallback 이 항상 성공**해 화면에 구멍이 원리적으로 안 생긴다.

### 타일 크기 512 유지

1024로 올릴까 검토했다가 취소. 근거가 "디스크 순차 읽기 효율"이었는데
소스가 RAM으로 확정되어 해당 없음. 재계산 결과 512가 VRAM(27 vs 40MB)과
예산 granularity(2ms에 28장 vs 7장)에서 유리하다.

### 포맷 — 소스 채널을 따라간다

| 소스 | 텍스처 | 변환 시점 |
|---|---|---|
| Gray | R8/R16 | **샘플링 시** (ImageGrayPS 가 `.r` 3채널 복제) |
| BGR 24bit | BGRA | **업로드 시** (24bit DXGI 포맷이 없어 저장 자체 불가) |
| BGRA | BGRA | 없음 |

원칙: **텍스처로 저장 가능한 포맷이 있으면 변환을 샘플링 시점으로 미룬다.**

### Single vs Tiled

D3D11에는 **부분 상주 텍스처가 없다**(밉 체인이 생성 시 전부 커밋).
그래서 타일링이 부분 상주의 유일한 수단이고, 판정은 "전량 상주 비용"으로 한다.

```
변 > 16384              → Tiled (하드 한계)
w·h·bpp·4/3 > 예산/뷰어수 → Tiled
그 외                    → Single (단순함이 이득)
```

### 샘플러를 2개로 나눈 이유

타일 텍스처는 배열 슬라이스 경계에서 CLAMP 된다. LINEAR 축소를 걸면
타일마다 테두리 텍셀이 번져 **이음새가 보인다.** Single 만 LINEAR 를 쓴다.

## 3. 발견한 이슈와 해결

| 이슈 | 해결 |
|---|---|
| **`Attach` 수명 계약에 안전한 해제 지점이 없음** — 뷰어가 호출자 버퍼를 빌려 쓰는데 언제까지 살려둬야 하는지 알 수 없음. 워커 풀 실험 중 실제 0xC0000005 로 재현됨 | `DetachImage()` 추가 (renderLock → 대기 업데이트 폐기 → 풀 해제 → ReleaseBuffer) |
| **`minZoom = 0.05f` 고정** — 40000px 이미지의 fit 배율 0.027이 하한보다 작아 휠 축소가 fit 앞에서 막히고 화면이 튐 | `GetMinZoom()` = `min(0.05, fitZoom)` |
| **`m_maxByteSize` 가 대입되지 않음** — early-return 무효라 업로드마다 raw 버퍼 재생성 | 대입 추가 + `>=` 비교 |
| **`EvictLRU` 가 현재 프레임 가시 타일을 뺏음** — `lastFrameUsed` 갱신과 `usedList` 순서가 어긋남 | `lastFrameUsed == frameID` 스킵 |
| **Hybrid CS 경로가 정작 필요한 곳에서 꺼져 있음** — 4096 스테이징 윈도우로 고LOD 타일 범위를 못 덮어 `lod<=3` 게이트 | 경로 자체 제거. GPU 는 이미 GPU 에 있는 데이터만 샘플링 가능 |
| **경계와 무관한 scratch clear** — 내부 타일도 매번 전체 clear (LOD0 에서 작업량 2배) | `TouchesBoundary()` 일 때만 |
| `ImagePS.hlsl` 주석이 CP949 로 깨져 있음 | UTF-8 로 재작성 (단 `.hlsl` 은 BOM 금지 — FXC 가 X3000 거부) |

## 4. 롤백한 것 — 타일 워커 스레드 풀

구현·검증까지 끝냈으나 **시기상조로 되돌렸다.**

- 현재 목표(16300²급 정지 영상)에서 이득이 얇음 (프라이밍 1회 10ms → 4ms)
- 축출 보호·취소·수명 3축이 모두 정확해야 하는 최고 리스크 구간
- 앞선 5~8단계가 **아직 육안 미검증**인데 그 위에 고위험 변경을 쌓는 형국

설계는 문서 §9 에 D1~D7 로 남겼다. 재도입 전제:
**5~8단계 육안 검증 완료 + 라이브 뷰/스트리밍 요구 확정.**

값어치가 나오는 지점은 30000px fit 줌 스트리밍(추정 37fps → 100fps)이다.

## 6. 주의사항

- **`.hlsl` 은 BOM 없는 UTF-8** — 프로젝트 규칙(UTF-8 BOM)의 예외. FXC 가 거부한다

- `Windows.h` 의 `min`/`max` 매크로 때문에 `(std::min)(...)` 괄호 형태 필요

## 이번에 배운 것 (다음 판단에 직접 영향)

### 프레임당 리소스 재생성은 이 하드웨어에서 비용이 아니다

세 번 연속으로 "매 프레임 생성/해제하니 느릴 것" 이라 판단했다가 측정에서 전부
효과가 없었다.

| 대상 | 전 | 후 |
|---|---|---|
| `TileManager::Configure` 풀 재생성 | 0.148 코어 | 0.211 |
| 사각형 지오메트리 (10k) | 1.462 코어 | 1.550 |

`CreateTexture2D(pInitialData = nullptr)` 는 VRAM 예약만 하고 초기화하지 않는다.
소형 D2D 객체도 마찬가지다. **비용은 드로우 콜에 있다** — 오버레이 프리미티브
하나당 420ns. 다음에 "재생성이 낭비" 라고 판단하면 먼저 측정할 것.

### 병목 위치 (실측)

```
유휴                     0.0%
이미지 렌더 (8192²)      0.4~0.55 ms   ← 크기와 무관
락 (프레임당 3~4회)      무경쟁, 무시 가능
오버레이 컬링            10 ns/개체
오버레이 D2D 드로우      420 ns/개체   ← 유일한 실질 병목
```

60fps 기준 화면 동시 표시 한계는 **프리미티브 약 40,000개**. 그 이상이 필요하면
D2D 개체별 드로우를 벗어나야 한다(단일 지오메트리 병합 또는 D3D 인스턴싱).
공간 인덱스는 필요 없다 — 컬링은 이미 충분히 싸다.

### 애니메이션이 "튄다" 는 신고의 원인은 세 가지였다

증상이 비슷해 보여도 원인이 달랐다. 순서대로 하나씩 실측으로 분리했다.

1. **유휴 후 첫 프레임의 dt** — 렌더 스레드가 잠들어 있어서 dt 에 유휴 시간이
   통째로 들어옴(0.1초 클램프). `k = 1-exp(-14×0.1) = 0.75` → 첫 프레임에 75% 소비.
   → `resumedFromIdle` 로 그 프레임의 dt 를 0 처리.

2. **표시 동기** — 60Hz 화면에 120fps 를 vsync 없이 밀어넣음. flip 모델에서
   `syncInterval=0` 은 티어링이 아니라 **프레임 폐기**다. 표시 간격이 불규칙해짐.
   → `Present(1, 0)`.

3. **보간 꼬리** — `IsAtTarget()` 임계가 절대값 1e-4 고정. 35프레임 중 뒤쪽
   16프레임이 이동량의 2.2% 만 처리 → 멈춘 듯하다가 툭 끝남.
   → "남은 변화 < 화면 1픽셀" 기준으로 변경.

추가로 **필터 전환이 zoom 1.0 에서 일어나던 것**도 원인이었다. 1024px 이미지의
fit 은 0.94 라서 휠 한 칸이 1.0 을 가로지른다(실측). 임계를 2.0/1.7 로 올림.

# 2026-08-25 — 공개 API 재설계

## 결정한 것

### 범위
- **8bit 센서 전용.** 의료 영상(12/16bit, Window/Level, DICOM)은 범위 밖.
  16bit Gray 경로는 이미 열려 있지만 이번 API 의 1차 대상이 아니다.
- **C++ 소비자는 기존 헤더를 그대로 쓴다.** C ABI 는 같은 DLL 안의 얇은 위임
  계층이고, 두 경로가 같은 `Impl` 구현을 공유한다. 로직을 C 계층에 두면
  동작이 갈라지므로 금지.
- **C#/WPF 바인딩은 이 저장소에 넣지 않는다** (사용자 결정, 2026-08-25).

### ROI 반환 형식 — 해석적 우선
정점 배열만 주면 원을 받아 다시 Set 할 때 다각형이 되어 편집 핸들과 계측
정확도(원 면적 = pi r^2)를 잃는다. 그래서 두 메서드로 나눴다.

| 용도 | 메서드 | 근거 |
|---|---|---|
| 계측 | `ROIGetShape` | 원본 파라미터 그대로, 무손실 왕복 |
| 마스킹/픽셀 순회 | `ROIGetVertices` | 곡선은 `segmentsPerCurve` 등분 근사 |

### 콜백은 락 밖에서
ROI 이벤트는 큐에 넣고 `m_roiLock` 을 놓은 뒤 디스패치한다. 호스트 핸들러가
콜백 안에서 ROI 조회 API 를 부르는 것이 자연스러운 사용법인데, 락 안에서
부르면 그대로 데드락이다.

### 마우스 콜백 호출 시점
뷰어 내장 UI(툴바/컨텍스트 메뉴) **다음**, ROI 편집 **앞**.
따라서 툴바 클릭은 호스트로 전달되지 않고, 호스트는 ROI 편집/팬/선택을
선점할 수 있다(`Handled = true`).

## 발견한 이슈와 해결

### ROI 이벤트 핸들러가 조용히 사라졌다
`Impl::SetROIEventHandler` 가 `m_roiLayer` 가 있을 때만 전달했다. 그런데
`Initialize` 가 레이어를 만들므로, **생성 직후 콜백부터 등록하는 호스트**
(C# 래퍼가 정확히 그렇다)는 등록이 통째로 유실됐다. 마우스 핸들러는 `Impl`
자신이 들고 있어서 살아남았고, 그래서 "마우스는 오는데 ROI 만 0회" 로 보였다.

→ `Impl` 이 핸들러를 보관하고 `ApplyPendingROIEventHandler()` 가 레이어 생성
직후 붙인다. **API 는 등록 순서에 의존하면 안 된다**는 일반 교훈.

### 공개 헤더에 BOM 이 없었다
한글 주석 + BOM 없음 → 소비자가 `/utf-8` 없이 컴파일하면 CP949 로 읽어
`error C2447` 로 죽는다. 우리 프로젝트는 `/utf-8` 을 켜 두어 안 보였다.
`D3D11ImageView.h`, `D3D11ImageViewC.h`, `IROIObject.h` 에 BOM 추가하고
`/utf-8` 없이 `/W4` 컴파일해 확인했다.

### 셰이더 경로는 CWD 의 "상위" 기준이다
`../Shaders/*.cso` 다. `x64\Debug` 에서 실행하면 `x64\Shaders` 를 찾는다.
없으면 `Initialize` 가 **로그도 없이** false 만 반환한다. 스모크 테스트가
여기서 한참 막혔다. 이미 기술 부채로 기록돼 있던 항목인데, 체감 비용이
생각보다 크다는 것이 확인됐다.

### 테스트 하네스 자체의 함정
`printf("%d %u", Call(&out), out)` 은 MSVC 가 인자를 **오른쪽부터** 평가해서
호출 **전** 값을 찍는다. 이것 때문에 정상 동작을 버그로 오인할 뻔했다.
호출과 출력을 같은 `printf` 에 섞지 말 것.

**오프스크린 타깃에 `DrawTextLayout` 은 아무것도 그리지 않는다.** 역시
HRESULT 는 전부 S_OK. 같은 자리에서 `Clear` 와 `FillRectangle` 은 정상이고,
엔진 컨텍스트든 새로 만든 전용 컨텍스트든 결과가 같다. `DrawText` 로 바꾸면
나온다. 원인은 못 밝혔고 코드 주석에 사실만 적어 뒀다.

**`FillOpacityMask` 는 앱을 죽였다.** A8 마스크 한 벌로 브러시만 갈아 끼우려
했는데 크래시. 값이 색을 결정하므로 색을 비트맵에 굽는 쪽으로 우회했다.

## `.sln` 을 일부만 커밋했다

작업 트리의 `.sln` 에는 `TestHost` 와 `D3D11ImageIO` 가 둘 다 등록돼 있다.
TestHost 는 저장소 제외 대상이고 D3D11ImageIO 는 빌드에 필요하다. 그래서
`D3D11ImageIO` 등록 11줄만 스테이징하고 TestHost 8줄은 작업 트리에만 남겼다.

**결과적으로 `git status` 에 `.sln` 이 항상 수정됨으로 뜬다. 정상이다.**
되돌리지 말 것.

이 때문에 로컬 빌드가 통과해도 증거가 못 된다. 형제 모듈이 보이는 위치에
새로 클론해서 Release 빌드로 확인했다(`Module/_verify_ImageView`, 확인 후 삭제).

## 알면서 남긴 것

**각도에 픽셀 스케일을 적용하지 않았다.** X/Y 배율이 다르면 화면 각과 실제
각이 어긋난다. 보정하려면 두 변 벡터에 스케일을 먹여야 하는데, 라인스캔
카메라를 실제로 붙여 보기 전에는 맞는지 확인할 방법이 없다.

**LUT 켜짐 상태에서 격자 글자 대비가 어긋난다.** 원본 값으로 판정하므로
`Inverted` 프리셋에서는 정확히 반대가 된다. 고칠 준비는 끝났다 —
아틀라스가 흰/검정 두 벌을 다 들고 있어서 `WantsDarkText()` 한 곳만
바꾸면 된다.
